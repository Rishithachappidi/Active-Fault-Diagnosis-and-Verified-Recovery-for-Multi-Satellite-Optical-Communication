Working out why a laser link between satellites failed, and whether it can be fixed

Rishitha Chappidi and Kaushal Reddy, October 2026. Built in MATLAB R2026a and Simulink.

Satellites can send data to each other with lasers. The beam is very narrow, so tiny pointing errors matter: at 800 km, an error of 20 microradians moves the spot about 16 metres.

When received power drops, re-pointing the terminal looks like the obvious fix. But weak power has several possible causes. The beam may be misaligned, the transmitter may have weakened, something may be in the way, or the angle sensor may be reporting the wrong direction. Re-pointing only helps with some of these. A correction that helped during a fault can also do harm once the fault has gone.

So for one simulated link we ask three separate questions. Is something wrong? What is wrong? Can the link be brought back? We started with a supervisor that answered the first question reasonably but the second one badly (we call it V1). Then we built a revised one (V2) and compared the two on the same faults and the same noise.

What we found

These numbers come from the MATLAB/Simulink runs: 4, 6, 8 and 10 satellites, 7 faults plus a no-fault case, 5 noise seeds, so 160 trials for each supervisor. They're the four-satellite averages. The other sizes give the same diagnosis scores, because the faulty link sees identical conditions in every network.

The low starting score for naming the fault wasn't a tuning problem. When we went through V1's code, it turned out it could only ever name one fault type, optical power loss. Every other fault came out as "something is wrong" or nothing at all. Averaging 66% on one fault type and 0% on the other six gives 9.5%.

The number that went down

One result looks worse at first: V1 recovers 10 of its 25 link outages before the fault clears, which is 40%. V2 recovers 5 of 20, which is 25%. The reason is that V2 stops five sensor-fault outages from happening at all, so they never enter its count, and what remains is harder to fix. Three of the faults can't be fixed by pointing anyway. With 82% power loss, even perfect alignment only delivers about 0.70 µW, below the 1.5 µW the receiver needs. In those cases V2 names the fault and sends traffic around the broken link instead of pretending to repair it.

Where V2 is worse

Now that V2 actually notices actuator faults, it also raises some false alarms around them. These happened during healthy periods in the actuator scenarios, where V1 had none: 4.7% for the weak-actuator fault and 4.0% for the slow one. V2 also takes longer to raise its first alarm, about 0.25 s against 0.02 s, because it waits for evidence before naming a cause.

How V2 tells faults apart

Sensor bias versus misalignment. The terminal has a separate rate sensor. V2 adds up the measured rate over time to get its own estimate of the angle. If the angle sensor suddenly disagrees with that running total, the sensor is the likely culprit, not the beam.

Weak actuator versus slow actuator. V2 compares the torque it asks for with the torque it gets over the last 0.8 s. Then it fits two numbers: how much torque arrives in the end, and how quickly. A weak actuator and a slow one change different numbers.

Misalignment versus lost power. When power is low and the cause is unclear, V2 nudges the beam a few microradians up, down, left and right. If power rises in one direction, the beam is misaligned and the fit says by how much. If power drops equally everywhere, the light itself is weaker.

Removing old corrections. V2 keeps predicting what the power should be, given its current explanation. If measurements disagree twice in a row, it drops the correction and checks the link again. This is what fixed most of V1's outages after the fault had cleared.

What it can't do

  • A completely dark link looks the same whether it's blocked, the transmitter is off, or the loss is very deep. V2 says "uncertain" here rather than guessing.
  • The sensor check only catches bias that appears after start-up. A bias present from the beginning goes unnoticed without calibration.
  • The actuator fit relies on accurate torque measurements, which real hardware may not provide.
  • The network layout is fixed, only one link is faulty at a time, there is no orbital motion, and traffic is modelled as a steady flow.
  • Everything here is simulation. None of it shows that this would work on a real satellite.

Running the MATLAB version

You need MATLAB R2026a with Simulink. From the project folder:

start_v2                  % opens the 4-satellite model
test_v2                   % runs the nine checks
folder = run_v2_suite;    % runs all 320 comparison trials
plot_v2_comparison(folder)

We reran the full 320-trial comparison on 16 October 2026 and got the same numbers as the saved batch, apart from run times.
